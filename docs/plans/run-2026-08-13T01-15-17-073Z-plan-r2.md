## (a) 处置决策

| # | 观察缺口 | 处置 | 理由 |
|---|---|---|---|
| 1 | **merge 后 task 状态仍 assigned，已合并任务的会话被续跑 sweep 继续投喂**（靠手动 dissolve 缓解） | **修** | 根因明确：`mergeNext`（merge.ts）成功后只写 merge_queue status="merged"，**不改 task.yaml.status**；continuation 的 `TERMINAL_TASK_STATUSES = {dissolved, failed, cancelled}`（continuation.ts:38）不含 "merged"，故已合并任务的席位仍被 `deriveContinuationTargets` 选中投喂。修复：merge 成功置 task.status="merged"，并把 "merged" 纳入终态集。小而明确、机制补全、有测试。 |
| 2 | **max_per_session 默认 0=不限 → 无任务角色（scout/sys-arch）被无界续跑烧 token** | **修** | 根因：config 默认 `continuation.max_per_session: 0`（config.ts:467）。平台席无 task 文件 → `taskIdOfAgent` 返回 null → 无终态门 → 每 idle_sec 必喂、无界。修复：默认改有界值（建议 5，长时自治 run 可显式调大）。小而明确、默认保守（与 prime-agent 默认 maxContinuations=3 同哲学）。 |
| 3 | **守护进程不热载新代码（合并后须重启）** | **修（观测+文档）** | 守护为长时进程，import 缓存使 TS dist 热载复杂且有中途退出风险（违背「无 daemon」不变量）。修复：runGuardian 记录启动时 repo HEAD，每 tick 对比；main HEAD 变化即置 `code_updated` 警告（含当前/基线 SHA），运维据此重启。不自动退出、不热载——保运行稳定。 |
| 4 | **serve DB 写错误偶发**（02:34 `Failed query: insert message`） | **缓（上游）** | 根因在 opencode serve 自身 DB 层，picode 侧无修复面；已有 P1 恢复 + 续跑幂等兜底。运维规程留档，跟踪上游。 |
| 5 | **checkpoint 快照 / maxTokens 计量**（ind-res 报告 M3-M8） | **缓（本轮不做）** | 大项：checkpoint 触及「快照 vs 文件真相」双源边界需先定义只读语义（sys-arch 评估）；maxTokens 依赖上游 token 契约（D058）。列 R3 候选，本轮不改。 |
