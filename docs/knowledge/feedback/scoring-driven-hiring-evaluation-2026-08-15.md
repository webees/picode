# 评分驱动招聘方案评估 + 改造方案（2026-08-15 · Sponsor 方案评估）

> 性质：**Sponsor 方案评估 + 改造设计**，作为下轮流程优化试点的输入（与流程简化审计配套）。
> 来源：sponsor 提问（评分系统是否有效、如何用于针对性招聘）+ run-lead 实测评估。
> 关联文档：docs/knowledge/feedback/sponsor-feedback-and-process-audit-2026-08-15.md（流程审计）、.picode/plans/audit-verification-report.md（审计验证）。

---

## 1. Sponsor 方案（原意）

**评分 → 人事档案（knowledge/hr/）→ 后续招聘针对性制定人设方案**——根据总工程师（run-lead）需求与项目需求，用历史评分档案指导新团队的人设/招聘设计。

## 2. 实测评估：方向正确，但回路从未闭合

### 2.1 现状证据（三轮 run 实测）

| 检查点 | 实测 |
|---|---|
| 评分档案建立 | ✅ 12+ 队、36+ codename 的 records 齐全（docs/knowledge/hr/personas/ + teams/） |
| **招聘时是否读评分档案** | ❌ **从未**——每轮 people 招聘 prompt 只要求"与 name-ledger 不冲突"，从不要求读 hr/teams 或 hr/personas |
| 高分 codename 复用（reuse_persona_ids） | ❌ 每轮全新 codename，零复用先例 |
| 低分项写入下轮禁区 | ❌ 归一 90（retries -5）的教训未被任何后续招聘引用 |
| 评分区分度 | ❌ C1-C4 全 95/100、三席全 100（仅归一 90）——同分无法指导"针对性" |
| 分数来源 | 流程信号（evidence/status/handoff/ack/retries）——**不反映人设内容质量** |

### 2.2 三个结构性原因

1. **公式无区分度**：全部满分区 → "高分画像"无差异可复用
2. **分数不度量人设质量**：95 分是"流程合规"分数，不是"这个人设写得好/执行得好"的质量分数——拿它指导人设方案，输入就是错的
3. **消费侧没接线**：招聘流程设计缺"读知识库画像"步骤（run-lead 流程遗漏，非 sponsor 方案问题）

## 3. 有效性判定

**方案要产生价值必须同时满足两个条件：**

| 条件 | 现状 | 改造 |
|---|---|---|
| ① 评分有区分度 | ❌ 全同分 | 公式加质量维度（handoff 质量等级 / evidence 完整性 / 打回次数） |
| ② 招聘强制消费评分 | ❌ 只写不读 | people 招聘 prompt 硬性要求：先读 knowledge/hr/ → 高分画像特征写入新团队人设（对标段）、低分教训写入 forbidden |

- 只满足①不满足② → 评分继续是仪式
- 只满足②不满足① → 招聘读到的全是同分，无指导意义
- **两个都满足 → 方案成立**：评分成为"人事智能"决策输入，招聘真正"针对需求"

## 4. 改造方案（下轮试点核心实验项）

### 4.1 评分公式改造（拉开区分度）

现有：base 50 + evidence/status/handoff/ack/retries（全合规即 95-100）
新增质量维度（±档位）：
- **handoff 质量等级**：evidence 完整性（log_ref 全可回查 +5 / 部分 -0 / 缺失 -5）
- **打回次数**（已并入 retries）保持
- **画像一句话**：每条评分产出 `profile: "强项：X；教训：Y"`（people 在评分时写，1 句）

### 4.2 招聘强制消费（回路闭合）

people 招聘 prompt 新增**硬性要求**：
1. 先读 `docs/knowledge/hr/teams/` 与 `personas/`（历史画像）
2. 新团队人设写**对标段**：引用 ≥1 个高分画像特征（如"沿袭 云岫 的 TDD 纪律"）
3. 低分教训写入新团队 forbidden（如"归一 round-1 零交付教训 → 必须分步提交"）
4. docs-qa 核验人设含画像引用（未引用 → 打回）

### 4.3 与流程简化结合（修正原审计建议）

- 原审计建议"评分取消或二值化" → **修正为"评分改造为决策输入"**（不取消，因为它是招聘优化数据底座）
- 评分产出精简为 3 件事：分数 + 一句话画像 + records 聚合（替换纯数字仪式）
- 解散后"评分+归档"合并：people 一次任务做"评分+画像"，docs 只做归档（省一次派发）

## 5. 试点验收口径（下轮）

- 区分度：同 run 内团队分数标准差 > 0（不再全同分）
- 消费闭环：100% 招聘任务的人设含画像引用段（docs-qa 核验通过率）
- 贴合度：人设画像引用与实际执行表现的相关性（定性观察，记录进 E 纪要）
- 与流程简化 A 级同轮执行，共用轮次消耗对比基线

## 6. 一句话总结

**Sponsor 方案方向正确且 picode 知识库早已预留此回路**——失败在执行（消费侧未接线）+ 公式无区分度。改造 = 公式加质量维度 + 招聘强制消费画像段，一轮试点即可验证方案真实价值。
