## 1. Sponsor 原始反馈（直接引述要点）

> "我们目前的流程设计，对于现在的 ai 是否太复杂繁重了？特别是三人组，深入分析当前设计是否存在过度设计，以及分析某些环节的必要性"
> "你需要将我和你对话的所有内容以及你的反馈都丢给 picode，让 picode 知道我们的反馈和想法，让 picode 自主升级"

**核心关切**：①流程仪式化成本过高（三人组/人设/交接包）；②怀疑存在过度设计；③希望反馈进入 picode 知识库并驱动自主升级。

## 2. Run-lead 审计结论（一句话）

**流程"骨架"（证据门禁、写集隔离、打回循环、变更单）经受住实战检验，一件不能少；"皮肉"（三人组、人设文档 12 字段、交接包六件套、评分公式）严重超重——同样的质量可用双人组 + 程序化人设 + 2 件交接包达成，轮次消耗预计省 30-40%。**

## 3. 实战数据（三轮 run：run-2026-08-15T01-12-43-3NZ / 02-30-00-DSH / 03-00-00-SUBAGENT）

## 5. 三人组逐角色审计

- **squad-lead**：价值最低（仅 C4 readJsonl 打回 1 次真实价值；其余为重复汇报/等待/被强催）；职责可并入 run-lead + 自动化检查 → **三人组 → 双人组（engineer + sdet）**
- **engineer**：核心不可替代；但会话失败率 ~10% → 保留 + 会话保活/接管预案
- **sdet**：**最不可省**（假绿暴露、基线对照、独立双跑、诚实打回全部实证）→ 保留，兼 diff/实现抽查（原 squad-lead 复核职责）

## 6. 简化建议（分级试点）

**A 级（下轮立即试点，零风险）**
1. 三人组 → **双人组**（engineer + sdet）；squad-lead 职责并入 run-lead（交接检查自动化：文件存在性 + git diff 命令）
2. 人设**程序化生成**：persona = 模板 + chunks.yaml 注入（写集/禁区/汇报对象）；删除手工人设与 staffing 合规仪式；双门闩合并为**单一简报批准**
3. 交接包**精简为 2 件**：evidence.yaml（保留）+ handoff.md（summary/known_issues/diff_scope 合并）
4. **重复汇报治理**：agent 收到"状态已知"确认后不再重发；报告只报增量

**B 级（试点后评估）**：评分取消或二值化；独立 code-review 仅 L/高风险。

**C 级（明确不做）**：证据门禁、打回循环、变更单、worktree 隔离——真实闸门，多起事故全靠它们拦住。

## 7. 风险与缓解

- 双人组失去"主责复核" → 复核职责给 sdet（验证席兼抽查）或 run-lead 合并门自动 diff 检查
- 人设取消后 codename 文化消失 → 属仪式，可保留 codename 但去掉 12 字段文档

## 8. 试点验收口径（下轮流程优化 run）

- 同一验收标准（全量绿 + evidence + 双门闩等价物）下，对比轮次消耗：**目标省 30-40%**
- 质量不降：证据门禁/打回循环/变更单全部保留，事故拦截率不降
- 试点 run 产出对比纪要（E 系列），数据驱动决策是否全量推广
